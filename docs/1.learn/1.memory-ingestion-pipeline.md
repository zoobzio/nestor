# Memory Ingestion Pipeline

This document specifies the architecture for Nestor's memory ingestion pipeline - the core system that transforms markdown content from agents into searchable, semantically-indexed memories.

## The Problem

Agents generate knowledge artifacts in markdown format. These artifacts contain structured information - headers, sections, code blocks - that needs to be searchable through semantic similarity. The challenge is transforming free-form markdown into indexed, embeddable chunks while preserving semantic coherence.

Nestor must:

1. Accept markdown content from authenticated agents
2. Parse and chunk the markdown intelligently (by headers/sections)
3. Generate vector embeddings for each chunk
4. Store both the raw memory and its searchable chunks
5. Return the memory ID for future reference

This is fundamentally a pipeline problem: sequential stages with reliability requirements, observable execution, and the possibility of partial failure.

## Pipeline Overview

```
|        |                 |                 |                 |                 |          |
|        v                 v                 v                 v                 v          |
|   [validate]        [store raw]      [parse md]        [generate]         [mark ready]   |
|   - customer ID     - memory to      - section         - vectors via      - update       |
|   - agent ID          bucket           boundaries        embedder API       memory        |

+-------------------------------------------------------------------------------------------+
                                            |

                              Triggered by: Memory.Created event
                              Executed by: WorkerPool (concurrency: 4)
```

## The Carrier: IngestJob

The carrier type flows through the entire pipeline. It holds everything stages need and accumulates state as processing progresses.

```go
// IngestJob is the carrier that flows through the memory ingestion pipeline.
// It tracks all state needed for processing and provides progress information.
type IngestJob struct {
    // Identity
    ID         string    // Job ID (UUID)
    CustomerID string    // Owning customer
    AgentID    string    // Submitting agent
    MemoryID   string    // Created memory ID

    // Input
    Content    string    // Raw markdown content

    // Progress tracking
    Stage      JobStage  // Current processing stage
    Status     JobStatus // Overall job status

    // Processing state
    ChunkIDs   []string  // Created chunk IDs (accumulated)

    // Metrics
    ChunkCount      int  // Total chunks created
    EmbeddedCount   int  // Chunks with embeddings

    // Error state
    Error      *string   // Error message if failed

    // Timestamps
    CreatedAt   time.Time
    StartedAt   *time.Time
    CompletedAt *time.Time
}
```

### Clone Method

The carrier must implement `Clone()` for parallel execution in worker pools:

```go
func (j *IngestJob) Clone() *IngestJob {
    c := *j
    if j.Error != nil {
        e := *j.Error
        c.Error = &e
    }
    if j.ChunkIDs != nil {
        c.ChunkIDs = make([]string, len(j.ChunkIDs))
        copy(c.ChunkIDs, j.ChunkIDs)
    }
    if j.StartedAt != nil {
        s := *j.StartedAt
        c.StartedAt = &s
    }
    if j.CompletedAt != nil {
        comp := *j.CompletedAt
        c.CompletedAt = &comp
    }
    return &c
}
```

## Stage Analysis

### Stage 1: Validate

**Purpose:** Guard clause - ensure the job has valid data before expensive operations.

**Input assumptions:**
- Job has CustomerID, AgentID, Content populated
- Content is non-empty string

**Operations:**
1. Verify customer exists (via contracts.Customers)
2. Verify agent exists and belongs to customer (via contracts.Agents)
3. Validate content is valid UTF-8
4. Check content size limits (configurable via capacitor)

**Output guarantees:**
- Customer and agent are valid
- Content is processable

**Failure modes:**
- Unknown customer: reject immediately
- Unknown agent: reject immediately
- Content too large: reject immediately
- Invalid UTF-8: reject immediately

**Reliability wrapping:** None needed - fast, local validation.

**Events:**
- `nestor.ingest.validate.started`
- `nestor.ingest.validate.completed`
- `nestor.ingest.validate.failed`

### Stage 2: Store

**Purpose:** Persist the raw memory before further processing.

**Input assumptions:**
- Validation passed
- CustomerID, AgentID, Content are valid

**Operations:**
1. Create Memory model with status "processing"
2. Store to database (sum.Database)
3. Store raw content to blob storage (grub.Bucket)
4. Update job.MemoryID with created ID

**Output guarantees:**
- Memory record exists in database
- Raw content stored in blob storage
- job.MemoryID is set

**Failure modes:**
- Database connection failure: retryable
- Blob storage failure: retryable
- Constraint violation: non-retryable

**Reliability wrapping:**
- Retry: 3 attempts with backoff (transient DB/storage failures)
- Timeout: 30 seconds

**Events:**
- `nestor.ingest.store.started`
- `nestor.ingest.store.completed`
- `nestor.ingest.store.failed`

### Stage 3: Chunk

**Purpose:** Parse markdown into semantic chunks.

**Input assumptions:**
- Memory exists with ID
- Raw content is available

**Operations:**
1. Parse markdown using chisel (markdown provider)
2. For each chunk:
   - Create Chunk model with MemoryID
   - Store chunk to database
   - Accumulate chunk ID in job.ChunkIDs
3. Update job.ChunkCount

**Output guarantees:**
- All chunks persisted to database
- job.ChunkIDs populated
- job.ChunkCount accurate

**Chisel chunking behavior:**

Chisel's markdown provider chunks by ATX-style headers (`#`, `##`, etc.):

```markdown
# Overview

Introduction text.

## Installation

Install instructions.

### Requirements

List of requirements.
```

Produces chunks:
1. `Kind: section, Symbol: "Overview", Context: []`
2. `Kind: section, Symbol: "Installation", Context: ["Overview"]`
3. `Kind: section, Symbol: "Requirements", Context: ["Overview", "Installation"]`

Each chunk includes:
- `Content`: The raw text of the section (including header)
- `Symbol`: The header text
- `Kind`: Always "section" for markdown
- `StartLine` / `EndLine`: Line boundaries
- `Context`: Parent header chain (hierarchical context)

**Failure modes:**
- Invalid markdown: non-retryable (log and continue with what parsed)
- Database failure: retryable
- Empty content: produces zero chunks (valid case)

**Reliability wrapping:**
- Retry: 3 attempts (database failures)
- Timeout: 5 minutes (large documents)

**Events:**
- `nestor.ingest.chunk.started`
- `nestor.ingest.chunk.completed` (includes chunk_count)
- `nestor.ingest.chunk.failed`

### Stage 4: Embed

**Purpose:** Generate vector embeddings for semantic search.

**Input assumptions:**
- Chunks exist with IDs in job.ChunkIDs
- Embedder service is available

**Operations:**
1. Load chunks from database
2. Batch chunks (configurable batch size via capacitor)
3. For each batch:
   - Call embedder.Embed(ctx, texts)
   - Update chunks with vectors
   - Store updated chunks
4. Update job.EmbeddedCount

**Nested pipeline pattern:**

The embed stage uses a nested WorkerPool with a different carrier type for batch processing:

```go
// embedWork is the carrier for the embed batch pipeline.
type embedWork struct {
    Batch    []*models.Chunk
    BatchIdx int
    MemoryID string
}
```

This allows bounded parallel embedding (e.g., 4 concurrent batches) without overwhelming the embedding API.

**Failure modes:**
- Embedder API unavailable: retryable (with circuit breaker)
- Rate limiting: retryable with backoff
- Partial batch failure: log error, continue
- All batches fail: fail stage

**Reliability wrapping:**
- Retry: 3 attempts with exponential backoff
- Timeout: 30 minutes (many batches possible)
- Circuit breaker: 5 failures, 30 second cooldown

**Events:**
- `nestor.ingest.embed.started`
- `nestor.ingest.embed.batch.completed` (per batch)
- `nestor.ingest.embed.completed` (includes embedded_count)
- `nestor.ingest.embed.failed`

### Stage 5: Finalize

**Purpose:** Mark the memory as ready for search.

**Input assumptions:**
- All chunks embedded
- Memory exists

**Operations:**
1. Update memory status to "ready"
2. Update job status to "completed"
3. Set job.CompletedAt

**Output guarantees:**
- Memory status is "ready"
- Job is marked complete

**Failure modes:**
- Database failure: retryable

**Reliability wrapping:**
- Retry: 3 attempts
- Timeout: 10 seconds

**Events:**
- `nestor.ingest.finalize.started`
- `nestor.ingest.finalize.completed`
- `nestor.ingest.finalize.failed`

## Pipeline Composition

```go
func NewPipeline() *pipz.Sequence[*IngestJob] {
    // Create base stages
    validate := pipz.Apply(ValidateStageID, validateStage)
    store := pipz.Apply(StoreStageID, storeStage)
    chunk := pipz.Apply(ChunkStageID, chunkStage)
    embed := pipz.Apply(EmbedStageID, embedStage)
    finalize := pipz.Apply(FinalizeStageID, finalizeStage)

    // Wrap with timeout
    storeWithTimeout := pipz.NewTimeout(StoreTimeoutID, store, 30*time.Second)
    chunkWithTimeout := pipz.NewTimeout(ChunkTimeoutID, chunk, 5*time.Minute)
    embedWithTimeout := pipz.NewTimeout(EmbedTimeoutID, embed, 30*time.Minute)
    finalizeWithTimeout := pipz.NewTimeout(FinalizeTimeoutID, finalize, 10*time.Second)

    // Wrap with retry
    storeReliable := pipz.NewRetry(StoreRetryID, storeWithTimeout, 3)
    chunkReliable := pipz.NewRetry(ChunkRetryID, chunkWithTimeout, 3)
    embedReliable := pipz.NewBackoff(EmbedBackoffID, embedWithTimeout, 3, time.Second)
    finalizeReliable := pipz.NewRetry(FinalizeRetryID, finalizeWithTimeout, 3)

    // Build sequence
    return pipz.NewSequence(PipelineID,
        validate,      // No retry - fast validation
        storeReliable,
        chunkReliable,
        embedReliable,
        finalizeReliable,
    )
}
```

## Worker Architecture

```go
type Worker struct {
    pool     *pipz.WorkerPool[*IngestJob]
    pipeline *pipz.Sequence[*IngestJob]
    listener *capitan.Listener
}

func NewWorker() *Worker {
    pipeline := NewPipeline()
    return &Worker{
        pool:     pipz.NewWorkerPool(WorkerPoolID, 4, pipeline),
        pipeline: pipeline,
    }
}

func (w *Worker) Start(ctx context.Context) {
    w.listener = events.Memory.Created.Listen(func(ctx context.Context, e events.MemoryCreatedEvent) {
        w.processJob(ctx, &IngestJob{
            ID:         uuid.New().String(),
            CustomerID: e.CustomerID,
            AgentID:    e.AgentID,
            Content:    e.Content,
            Stage:      JobStageValidate,
            Status:     JobStatusPending,
            CreatedAt:  time.Now(),
        })
    })
}

func (w *Worker) processJob(ctx context.Context, job *IngestJob) {
    jobs := sum.MustUse[contracts.IngestJobs](ctx)

    // Mark started
    job.Status = JobStatusRunning
    now := time.Now()
    job.StartedAt = &now
    _ = jobs.Save(ctx, job)

    events.Ingest.Started.Emit(ctx, events.IngestStartedEvent{
        JobID:      job.ID,
        CustomerID: job.CustomerID,
        AgentID:    job.AgentID,
    })

    // Execute pipeline
    result, err := w.pool.Process(ctx, job)
    if err != nil {
        errStr := err.Error()
        job.Error = &errStr
        job.Status = JobStatusFailed
        _ = jobs.Save(ctx, job)

        events.Ingest.Failed.Emit(ctx, events.IngestFailedEvent{
            JobID: job.ID,
            Stage: string(job.Stage),
            Error: errStr,
        })
        return
    }

    result.Status = JobStatusCompleted
    now = time.Now()
    result.CompletedAt = &now
    _ = jobs.Save(ctx, result)

    events.Ingest.Completed.Emit(ctx, events.IngestCompletedEvent{
        JobID:      result.ID,
        MemoryID:   result.MemoryID,
        ChunkCount: result.ChunkCount,
    })
}
```

## Design Rationale

**Q: Why store the raw content before chunking?**

The raw content is the source of truth. If chunking logic changes or embeddings need regeneration, having the original content available enables reprocessing without re-ingestion. The blob store is cheaper than the database for large text content.

**Q: Why a separate MemoryChunk model rather than embedding chunks in Memory?**

Chunks need independent vector indexing for semantic search. They also need their own lifecycle - a single memory produces many chunks, and queries return chunks, not full memories. The many-to-one relationship is fundamental.

**Q: Why use a nested WorkerPool for embedding?**

The embedding API is the bottleneck. A dedicated pool with bounded concurrency prevents overwhelming the API while maximizing throughput. The outer pipeline processes jobs sequentially through stages, but embedding parallelizes within the stage.

**Q: Why no cancel check between stages?**

Unlike vicky's code ingestion (which can take 30+ minutes), memory ingestion is fast (typically under 1 minute). The complexity of cancellation support is not justified. If a job fails, the memory is marked failed and can be retried.

**Q: Why Validate as a separate stage rather than inline?**

Separation enables:
- Clear error reporting ("failed at validate" vs "failed at store")
- Future expansion (e.g., content moderation)
- Consistent event emission per stage
- No wasted work (validation fails before any storage)
